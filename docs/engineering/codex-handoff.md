## Accepted deployment and commercial architecture — not implemented by this task

APBRA Cloud is an APBRA-managed multi-tenant target profile. APBRA Dedicated uses an isolated customer cloud/account or hosted environment under an agreed operator model. Qualified APBRA Private / On-Premises runs inside the approved customer boundary. Air-gapped operation is future and requires explicit qualification. Azure is a reference/private-preview deployment profile, not a mandatory core dependency. Identity, storage, networking, inference egress, secrets, telemetry, backup/recovery, updates and target connectivity require profile-specific evidence before a profile is called supported.

A future central commercial/control plane may keep minimum organisation/deployment catalogue, stable `deployment_id`, subscription/edition, versioned entitlements, licence status/expiry, release channel and safe deployment/licence metadata. Customer users and mappings, Tenant Settings, protected credentials, evidence/source data, prompts and conversation, accepted requirements, report artifacts and Delivery Guides, customer audit/history and operational content remain in the selected **customer data plane**. Subscription validation must not upload that content or create a central content back door. `deployment_id` identifies an installation/licence lifecycle; `tenant_id` identifies a company security domain. One Cloud deployment may host multiple tenants; Dedicated/Private relationships are separately qualified. The current local/CI PostgreSQL database is not a central SaaS licensing store.

Commercial availability follows **Subscription → versioned Entitlements → stable Capabilities**. Effective capability intersects installed/qualified platform support, entitlement, Tenant Settings, user/application permission, resource-specific permission and current security/validation/governance. Paid access never bypasses authorization, tenant isolation, private-resource access, target-platform validity, deterministic checks, release policy or deployment authority. A future resolver should use stable capability keys, not marketing plan-name branches. Exact plans, prices, quotas, grace periods, billing provider and licensing mechanics remain undecided and require separate authority.

Power BI remains a first-class current output adapter. APBRA-165's future versioned APBRA Report Definition (ARD), native renderer/live canvas and other adapters are not implemented. No PBIX generation or universal translation is inferred from today's PBIP path. NO HARDCODING applies to customer-varying provider, model, region, deployment, tenant policy and commercial choices; fixed schemas, supported capabilities and security/validation invariants remain fixed contracts.
